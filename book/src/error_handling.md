# Handle validation errors

Koruma supports two error views: strongly typed accessors for normal application code and a flat
`ValidationIssues` view for generic form or adapter code. Typed accessors retain delegated nested
and newtype error trees; structured issues summarize those delegated trees at the parent field.

## Inspect typed failures

After deriving `Koruma`, `validate()` returns a generated error type named after the validated
struct. For `Item`, the return type is `Result<(), ItemKorumaValidationError>`. Each field error
group exposes one accessor per validator and an `all()` iterator:

```rust,ignore
if let Err(errors) = item.validate() {
    for failed in errors.age().all() {
        println!("age validator: {}", failed);
    }

    for failed in errors.name().all() {
        println!("name validator: {}", failed);
    }
}
```

This pattern is useful when a field has multiple rules and you want to show every failure instead of
only the first one. Koruma does not stop checking the remaining validators for a present target
after one fails. `all()` yields stored direct-validator failures in source order and returns
borrowed values, so inspecting every failure does not require the validator types to implement
`Clone`.

Derive `KorumaAllDisplay` when the values returned by `all()` must implement `Display`. Every
stored validator then needs its own `Display` implementation. Derive `KorumaAllFluent` instead when
the values must implement `FluentMessage`.

## Enumerate structured issues

For tooling that wants a generic, field-scoped view instead of strongly typed
accessors, generated aggregate error structs implement `ValidationIssues`.
`errors.issues()` returns direct field and element issues with field names,
available as typed `ValidationFieldName` values, validator type names, labels,
element indices, and fallback messages. A failed nested or newtype field produces
one parent-level summary issue. To enumerate its individual failures, obtain the
delegated error through the typed nested or newtype accessor and, when that
error implements `ValidationIssues`, call `issues()` on it. Errors generated by
`#[derive(Koruma)]` provide that implementation. Parameter-aware tooling can use the strongly typed
failed-validator getter and `ValidatorMetadata::validator_params()` to read
runtime validator parameters.

```rust,ignore
use koruma::ValidationIssues as _;

if let Err(errors) = item.validate() {
    for issue in errors.issues() {
        let field = issue.field_name_str().unwrap_or("<form>");
        if let Some(index) = issue.element_index() {
            println!("{field}[{index}]: {}", issue.message());
        } else {
            println!("{field}: {}", issue.message());
        }
    }
}
```

Structured issues carry fallback messages for generic reporting. When a generic UI also needs the
configured `min`, `max`, or other validator arguments, read them from the typed failed-validator
accessor with `ValidatorMetadata::validator_params()`.
